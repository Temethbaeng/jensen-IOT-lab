# Reflektionsdokument – obligatorisk leverabel

Svara kort men motiverat på samtliga frågor. Knyt svaren till vad du implementerade och observerade i laborationen; enstaka ja/nej-svar är inte tillräckliga. Ersätt instruktionstexten med dina svar före inlämning.

1. Varför ska sensorerna kommunicera med ett API i stället för direkt med PostgreSQL? Det handlar egentligen om att ha ett kontrollerat mellanlager, APIt ger mig ett ställe där tre saker sker. "Reglerna finns på ett ställe": validation.py och det gäller alla sensorer, skulle varje sensor skriva direkt till databasen så måste varje sensor individuellt implementera samma regler och sen hålla dom synkade när det ändras vilket kan skapa problem om de glider isär. "Kontrollen av okända sensorer": mitt device_exists-anrop stoppar sensor-999 med ett tydligt 400. Utan APIt hade databasen fått avvisa den via främmande nyckeln, och klienten hade fått ett obegripligt databasfel. "Åtkomsten är begränsad": Kolla docker compose ps  databasen exponerar bara 5432/tcp internt, ingen port ut. Sensorerna kan bara nå APIt, och APIt kan bara göra det jag programmerat. Direktåtkomst hade krävt att varje fältenhet bär databasinloggning, och den som kommer åt en sensor kommer åt hela databasen med rätt att läsa och radera allt, inte bara skriva en mätning.
2. Varför ska felaktig sensordata stoppas innan den sparas? Felaktig sensordata ska stoppas innan den sparas för att bibehålla datakvalitet, minimera kostnaden att städa i efterhand och effektivisera återkopplingen. Sensor-003 skickar med flit felaktiga värden. Sparades de skulle medelvärdet bli missvisande, och ingen som läser siffran senare skulle veta om det. Ett felvärde som skrivits in måste hanteras vid varje läsning, för alltid vilket gör att det blir mer handpåläggning och kostar mer tid. Varje SQL fråga, varje rapport måste veta vilka rader som är skräp och vilka som inte är det. Och har man en fungerande återkoppling så får den som felsöker veta exakt vad som är felet direkt som i detta fall med min API där den svarar "400" med "temperature must be a number".
3. Varför passar PostgreSQL för historiska mätvärden? PostgreSQL är relationellt vilket betyder att datan ligger i rader med kolumner och man kan ställa frågor emot dom. Datan ligger på disk i volymen som har en egen livscykel skild från containrarna vilket gör den beständig. Jag testade COUNT(*) som gav 4513 rader, AVG(temperature) som gav mig 21,38 och en tidsfiltrering på senaste dygnet samt att rad 1891 kom tillbaka oförändrad efter docker compose down och omstart.
4. Vad händer med lösningen om Redis försvinner? Om redis försvinner så fortsätter allt att fungera. Ingen data går förlorad för redis håller bara en kopia av något som redan finns i databasen, det enda som egentligen tar stryk är prestandan. Varje läsning måste gå till PostgreSQL tills cachen byggts upp igen.
5. Vad händer med lösningen om PostgreSQL försvinner? Om PostgreSQL försvinner så försvinner all historik. Kvar finns endast det som redis har och det är en per sensor. Fråga 4 och 5 hänger ihop på det sättet. Redis är en kopia som kan återskapas medans PostgreSQL är orginalet som inte kan det.
6. Varför används Docker Compose lokalt? Compose startar fyra tjänster med ett kommando istället för fyra manuella "docker run" med nätverk och miljövariablar. Konfigen ligger i versionshanterad kod så det är lätt att reproducera miljön = vem som helst som klonar repot får densamma uppsättning.
